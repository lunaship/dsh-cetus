# G4.0 复核：回环鉴权不是方案 A 的前提

状态：**复核完成，原结论作废。G4.1 / G4.2 解除停止。** 传输实现改用回环桥 + 系统内层 TLS（与 Android 同构，见文末「决定」）。

复核对象：`docs/ios/I5.2-spike.md` 中「G4.0 回环鉴权未通过」的结论，及其在 `docs/ios/PLAN.md`、`docs/ios/CONTINUE.md` 里派生的停止条件。

## 原结论是什么

G4.0 用 `apps/ios/Tests/LocalGatewayAuthTests.swift` 探测 HTTP 代理能否在转发内层 TLS 之前完成鉴权，结论是：

> G4.0 已实测并停止：系统 URLSession 会绕过 `127.0.0.0/8` 的代理，也没有可插入现有 `HostClient` 路径的 TLS 前鉴权层。非回环 CONNECT 不能代替要求的回环地址。

由此推导出「方案 A 不可行，停止 G4.1 / G4.2」。

## 测试实际证明了什么

`LocalGatewayAuthTests` 只有一条测试 `correctCredentialReachesTLSAndBadCredentialsDoNot`，四段断言：

| 段 | 目标 | 断言 | 结果 |
| --- | --- | --- | --- |
| 1 | `10.255.255.1` + 正确口令 | 代理收到 `Proxy-Authorization`，并转发出 TLS 握手首字节 | 成立 |
| 2 | 同一目标 + 错误口令 | 代理回 407，不建立隧道 | 成立 |
| 3 | 同一目标 + 无口令 | 超时，不建立隧道 | 成立 |
| 4 | `127.0.0.1` + 正确口令 | 代理**没有**收到任何连接，直连到 443 | `direct == 2`，成立 |

前两段结论有效：**HTTP 代理确实能在 TLS 之前做鉴权**。问题出在第 4 段的用法。

第 4 段真正证明的命题是：

> 当目标主机是 `127.0.0.1` 时，`URLSession` 不经过 `proxyConfigurations`，直接连目标端口。

这是一个关于**代理与回环地址**的事实，不是关于**方案 A 可行性**的事实。

## 为什么这个前提是多余的

RFC 0001 §6.1「来源判定：不以回环地址做授权」把授权位置写得很清楚，而且**明确禁止**用回环地址做授权判断：

1. **不变量**：18640 上任何授权判断都不得依赖「对端是回环地址」。现有 `PANEL_ONLY_PATHS` 按路径屏蔽，满足此不变量，必须保持。
2. Agent 在本地 socket `connect` 事件中，以该 socket 的 `localPort` 为键登记 `remoteOrigins.set(localPort, { kind, deviceId?, bootstrapId?, sid })`，在 `close` 时删除。插件处理请求时：对端为回环地址且 `req.socket.remotePort` 在表中 → 远程来源；否则为 LAN 来源。

也就是说，**DLP/1 的授权发生在电脑端的端口登记表，不在手机端**。手机侧不需要、也不应该提供一个「TLS 前鉴权层」。

代码已经按 §6.1 实现：

- 插件侧：`src/index.js` 用 `agent.originOf(socket?.remotePort)` 判定来源，并注明「只在对端是回环地址时查来源表」。
- Android 侧：`grep -rn 'Proxy-Authorization' apps/android/` **无任何命中**。Android 的远程路径完全不使用代理。

所以 G4.0 测的是一个**在产品里不存在的机制**。它失败不构成方案 A 的失败。

## 那 iOS 真正的差别是什么

差别只有一处，且不在协议里，在实现手段上：

| | Android | iOS |
| --- | --- | --- |
| 怎么把隧道接到 HTTP 栈 | 自定义 `Socket` 子类（`TunnelSocket`），`socketFactory()` 注入 OkHttp | `URLSession` 不允许注入自定义 socket |
| 上层 HTTP / SSE | 原样复用 | 原样复用 |

Android 的 `WebSocketTunnelSocketFactory.TunnelSocket` 做的是：`connect()` 里开外层 WSS 与会合；再在本机起一个临时 `ServerSocket`（只绑 `127.0.0.1`），自己连上去、写一个 32 字节随机 secret 完成本地对接；之后这个「假 socket」的读写就是隧道字节流。

**这一整套是为了在 socket 层嫁接，好让 OkHttp 毫不知情。它是一个实现技巧，不是协议要求。**

iOS 缺的只是「能从 socket 层嫁接」这一点。它并不缺「把 HTTP 字节送进隧道」的能力。

## 复核结论

1. 「G4.0 回环鉴权未通过」成立，但它证明的是代理与回环地址的关系，**不是方案 A 不可行**。
2. RFC 0001 §6.1 把授权放在电脑端，手机端不需要 TLS 前鉴权层。该前提从设计上就不存在。
3. 方案 A 的协议部分（RFC 0001、relay、插件 Agent、DLP/1 加密与帧）**全部已实现并通过测试**，与本结论无关。
4. 需要改的只有 iOS 侧「把字节接到 HTTP 栈」的手段。

因此原「停止 G4.1 / G4.2」的派生结论作废。

## 决定：iOS 用回环桥 + 系统内层 TLS（与 Android 同构）

**本节在实现阶段被修正两次，记录在此以免后人重走。**

### 被否掉的两次尝试

**第一次：`URLProtocol` 接管。** 思路是「iOS 不给换 socket，那就退到 HTTP 层接管」。实现到一半发现它跳过了 `URLSession` 的真实建连，于是没有 socket 可叠内层 TLS；而 RFC §4.2 第 6 步要求**手机在管道上做内层 TLS（钉扎插件证书）**，§4.3 也写明 `x-dsh-link-token` 在「内层 TLS 内」传输。内层 TLS 不可省，此路不通。

**第二次：`NWConnection` 一条栈走完。** 思路是「`NWProtocolWebSocket` 做外层 WSS、`NWProtocolTLS` 做内层」。实现到一半发现协议栈理解错了：**外层 WSS 与内层 TLS 是串联，不是并列**。两者都只能挂在同一段真实 transport 上，无法表达「先跑完 WS，再在同一个连接上叠 TLS」。且 `NWParameters` 没有「无 transport」的构造，`NWProtocolFramer` 只能塑形某段真实 transport 的字节、不能当栈底，`NWConnection` 因此**不能骑在已有字节流上**。

### 结论

iOS 上没有任何「把 TLS 叠到一段外来字节流上」的公开 API。与 Android 的差别就在一个 API：

```kotlin
// Android HostHttp.kt:568-570
.socketFactory(WebSocketTunnelSocketFactory(remote, offset))                 // 裸连接 = 隧道
.sslSocketFactory(pinnedContext(trustManager).socketFactory, trustManager)   // 内层 TLS 叠在它上面
```

Java 给了 `SSLSocketFactory.createSocket(raw, host, port, false)`（`HostHttp.kt:515` 的 LAN 探测用的是同一个）。iOS 没有对应物。

因此 iOS 必须有一个回环桥：把隧道字节喂到一个本地端点，让**系统 TLS 栈**在那个端点上做内层 TLS。

**Android 本来就是这么做的。** `WebSocketTunnelSocketFactory` 内部的 `TunnelSocket.openGateway()` 就是回环桥——`ServerSocket(0, 4, 127.0.0.1)`（第 137 行）+ 一次性 32 字节 secret 认亲 + `local.connect(127.0.0.1:server.localPort)`（第 168 行）。桥不是 iOS 的额外负担，它是两端共用的结构。

### 实现形状

1. 外层 WSS + DLP/1 会合：`NWConnection` + `NWProtocolWebSocket`。
2. 桥：`NWListener` 只绑 `127.0.0.1`，一次性随机 secret 认亲，生命周期与隧道绑定（隧道关闭时桥必须一起关）。
3. 内层 TLS：对桥的本地端点建 `NWConnection`，`NWProtocolTLS` + `sec_protocol_options_set_verify_block`，**只认插件叶证书指纹**，复用 `DLSecurity.PinEvaluation`。TLS 由系统实现，不写 TLS。
4. TLS 之上：HTTP/1.1 序列化与解析（`HTTP1Wire`），SSE 走 `SSETransport` 的一个新实现。

### 桥不承担信任职责

桥只绑回环、secret 一次性、生命周期跟隧道同生共死。**身份保证完全来自内层 TLS 的证书钉扎（§4.3），桥本身不是信任边界**——与 Android 一致。实现与评审时都要显式说明这一点。

### 不选其余路径的理由

- **方案 B（SwiftNIO）**：要自写最小 HTTP/1.1 客户端与 SSE 解析，是重复劳动；RFC 0001 自己也写明「协议并没有要求这样做」。
- **不做内层 TLS**：违反 §4.2 第 6 步与 §4.3（token 会明文过 Relay），除非改协议，不能交付。
- **Tailscale**：保留在选路链里（局域网 → Tailscale → 中继），RFC §3 已说明为何不作为唯一手段（要求两端都装第三方 VPN，与代理类 App 冲突）。

## 验证手段：纯逻辑层可以脱离 iOS 环境真跑

CI 的 iOS 作业要排 macOS runner，本地又受 `CetusTests` 的 swiftmodule 问题所限，
很容易把所有验证都推给 CI。但**依赖只有 Foundation 的那几层不需要等 CI**——把它们直接
编成 macOS 可执行文件就能在本机真跑（不是类型检查）：

```bash
# 1) 把只依赖 Foundation 的 Swift Package 编成 macOS 模块
xcrun swiftc -emit-module -emit-library -module-name DLRemote -swift-version 5 \
  -emit-module-path mod/DLRemote.swiftmodule -o mod/libDLRemote.dylib \
  Packages/DLRemote/Sources/DLRemote/*.swift

# 2) 编译生产源码 + 测试驱动，本机执行
xcrun swiftc -o probe -swift-version 5 -I mod -L mod -lDLRemote \
  Packages/DLNet/Sources/DLNet/Remote/HTTP1Wire.swift \
  Packages/DLNet/Sources/DLNet/Remote/RemoteTunnelPool.swift main.swift
DYLD_LIBRARY_PATH=mod ./probe
```

适用范围（G4.1 实测）：`HTTP1Wire` 的请求组装与响应解析、`RemoteTunnelPool` 的 §5.8 限额、
`DLSecurity` 的指纹判定——这些是「一次 HTTP 请求经隧道」里全部的纯逻辑部分。

**不适用**：内层 TLS 握手、回环桥对泵、DLP/1 会合时序——它们依赖 Network.framework 与
真实 TLS 服务，只能在 CI 或真机上验。

价值在于：G4.1 实现中有 4 个 bug（`NWListener.port` 时序、多余的 secret 认亲、
`start()` 互等、接收循环未被调用）**全部落在这个「不适用」区间**，而纯逻辑层真跑之后
是干净的。先把能真跑的跑绿，能把注意力集中在真正危险的那一小块上。

## 边界

- 本复核不改协议、不改 relay、不改插件 Agent、不改 DLP/1 加密与帧。
- 不连 `relay.dshlinks.com`；开发与验收用隔离 `stateDir` 的 host 与本地 `relay/`。
- 真机、蜂窝切换与线上送达仍属 G7。
