# I5.2 Spike：选方案 A（每条 TCP 一条 WSS 的连接池）

状态：**G4.0 原结论已复核作废**（见 [`G4.0-review.md`](G4.0-review.md)）。G4.1 / G4.2 解除停止，iOS 传输改用 `URLProtocol` 接管。不引入 SwiftNIO。

基线：`origin/ios/main` @ `39ce9d45`。对照 RFC 0001 §4.2、§5.8、§7.2–§7.3，以及 Android `WebSocketTunnelSocketFactory` + `HostHttp.buildRemoteClient`。

## 结论

推荐 **方案 A**。RFC 不支持一条 WSS 上多路复用，所以 A 必须是连接池：`URLSession` 每新建或复用一条到回环桥的 TCP，桥就为它单独开一条外层 WSS，完成一次 `client_open` → `ready`，再原样搬字节。不是在一条 WSS 上叠多条 DLP 流。

方案 B 留到下面「什么时候才改 B」的条件成立时再做。

## 为什么不是多路复用

RFC §4.2 的合同是「一流两 WSS，Relay 只拼接」：

1. 手机每条 TCP 新开一条客户 WSS，发一条 `client_open`。
2. Relay 分配一个 `sid`，经电脑的控制连接推 `open`。
3. Agent 另开一条数据 WSS，发 `host_accept`。
4. Relay 把这两条 WSS 拼成一条字节管道，两端收到 `ready` 之后只转发二进制帧。

一条客户 WSS 对应一条流。§5.4 没有流 id 复用、没有子流窗口，数据阶段出现文本帧是 `PROTOCOL_ERROR`。多条流共用一条 socket 必须自做按流流控，否则慢消费者堵住整条连接（§4.2「为什么不多路复用」）。一流一 socket 时，写不进去就不再读，背压沿 TCP 回去。

因此 PLAN 里「待核实：一条 WSS 能否承载多条并发流」的答案是 **不能**。不支持时不必改 B：A 的回环桥本来就是「每来一条 TCP，开一条 DLP/1 流」。

## 方案 A 怎么接

和 Android 同一形状，只是外层库不同。

| | Android（已上线） | iOS 方案 A |
| --- | --- | --- |
| 谁发起一条流 | OkHttp 向 `SocketFactory` 要一条 socket | `URLSession` 向回环地址建一条 TCP |
| 一条流几条 WSS | `connect()` 里 `newWebSocket` 一次 | 该 TCP 的 accept 路径里开一个 `URLSessionWebSocketTask` |
| 会合 | 等 `hello` → `client_open` → `ready`，总超时不超过 10 秒 | 同左，帧与 MAC 用 I5.1 |
| 内层 TLS | 钉扎插件证书的 `SSLSocketFactory`，盖在这条裸 socket 上 | 钉扎逻辑仍是 I3.4；远程主机写成 `https://127.0.0.1:<端口>` |
| HTTP / SSE | 同一套 OkHttp | 同一套 `HostClient` / `SSEClient` |
| 连接池 | `ConnectionPool(3, 50, SECONDS)`，复用的是已经会合完成的隧道 | `URLSession` 对回环源的 HTTP keep-alive；池里一条空闲 TCP = 一条仍开着的 WSS |

Android 的外层 OkHttp 只负责这一次 WSS 握手，不在这条 WSS 上再跑 HTTP。内层 HTTP 跑在回环网关对面的那条真实 socket 上（RFC §7.3）。iOS 不要把「URLSession 自己的连接池」理解成可以在一条 WSS 上复用多个请求：复用单位是回环 TCP，一条 TCP 背后始终是一条已 `ready` 的 WSS。

不预热。Relay 对 5 秒内不发首条消息的连接以 `4000` 关闭（§5.8、§10.3）。池里只保留已经完成会合、并且内层 HTTP 还握着的隧道。

## 连接池怎么守 §5.8

池子守的是 **现行 §5.8**，不是文首变更摘要里的旧数字。摘要第 9 行写「每设备 6、每 route 32」，那是 v2 初稿。2026-09-30 因空闲连接也占流，§5.5 与 §5.8 已把每设备并发从 6 改为 12（变更记录）。「每 route 32」也没有落在现行表里：现行是每 route **64**（Relay，含待接受），每台电脑 **32**（Agent）。按 6 做池会把 keep-alive 余量挤没；按 32 做池会把一台手机当成整台电脑的额度。

App 不执行 Relay 的每 route 64，也不执行 Agent 的每台电脑 32。手机守本设备 12，并给电脑那 32 留出余量。

| 限额（现行 §5.8） | 谁执行 | 手机侧怎么守 |
| --- | --- | --- |
| 每设备并发流 **12**（旧值 6 已废） | Agent，数活跃流；满了回 `DEVICE_LIMIT` | 本机预算 ≤ 12。空闲隧道也算（§4.2 keep-alive 合同） |
| 每台电脑并发流 **32** | Agent，本机活跃流 ≥ 32 回 `SERVER_BUSY` | 不在手机上按 route 计数。32 是这台电脑上所有手机的总额 |
| 每 route 并发流 **64**（含待接受；旧摘要里的 32 不是这一档） | Relay，超出回 `4005 SERVER_BUSY` | 手机只退避，不自己实现这道闸 |
| 插件空闲上限 65 秒 | 插件 HTTP | 客户端空闲保留 **50 秒**，短于 65 秒，由手机先放手 |

Android 已经把 12 拆成可以同时成立的三块（`HostHttp` 注释与 `RemoteGate`）：

- 空闲池 **3**
- 短请求在途 **4**（`RemoteGate.PERMITS`；响应体关闭才归还）
- SSE **2**（长连接不占短请求名额，否则一条订阅吃掉整个闸门）

3 + 4 + 2 = 9，严格小于 12。多出来的 3 条留给建连重叠和对端计数窗口，不作为可配置上限。iOS 用同一组数：`URLSessionConfiguration` 对回环源 `httpMaximumConnectionsPerHost = 9` 只是硬顶；真正的预算仍是「空闲 ≤ 3、短请求在途 ≤ 4、本主机 SSE ≤ 2」。不要把 `httpMaximumConnectionsPerHost` 设成 32 或 64。

空闲 50 秒与 RFC §4.2 对齐：插件 keep-alive 空闲上限 65 秒、`headersTimeout` 66 秒，必须由客户端先关。关早了会多一次会合；留到 65 秒以后，会撞上服务端先关，复用竞态把请求打进半关连接。

撞上 `DEVICE_LIMIT`（本设备 12）、`SERVER_BUSY`（电脑侧 32 或 Relay 侧每 route 64）、`RATE_LIMITED` 时，按 §5.7 / §7.2 在 **同一条远程路径** 上退避重试，不切局域网、不清选路缓存、不删凭据。这三档是「这条路暂时满了」，不是「这条路不通」。

## 为什么仍是 A 而不是 B

连接池补上了 PLAN 里唯一的协议疑问，A 的理由还在：

- 不引入 SwiftNIO、NIOSSL、NIOWebSocket、NIOTransportServices（PLAN 依赖表：这些只在方案 B 才进入）。
- 内层 HTTP、SSE、`Last-Event-ID`、证书钉扎继续用已经落地的 `URLSession` 路径（I3.4、I3.5）。远程与局域网只差 socket 下面是直连还是回环桥。
- 背压沿用「写不进对端就停读」。Android 在 WebSocket 读线程里阻塞写网关 socket（§7.3）；iOS 同样让 WSS 的收方向回环 TCP 的写对齐，不在桥里做无界缓冲。
- 二进制帧上限仍是 256 KiB，发送端按 ≤ 64 KiB 切（§5.4.4）。这是搬运参数，不是新的多路复用层。

B 要自己写最小 HTTP/1.1 客户端和 SSE 解析，并在 NIO 上重做一遍内层钉扎。协议并没有要求这样做。

## 什么时候才改 B

只有实测证明「每条 TCP 一条 WSS」做不到，并且换池参数解决不了，才停 A、改 B。触发条件是下面任一：

1. `URLSessionWebSocketTask` 不能对一条已打开的任务做阻塞式背压：对端停读时，本机仍无界排队，RSS 按 RFC §13.2 的慢读用例涨过 16 MB 量级，而且收紧池大小无效。
2. 系统 WSS 无法关闭压缩，或无法按 `outerPin` 校验外层叶子指纹，导致外层身份只能信任系统 CA、自建钉扎中继无法落地。
3. 回环桥做不到「TCP 半关 ↔ WSS 关闭」对齐，SSE 或下载的 EOF 丢失，且不能在桥内补上（Android 是 `shutdownOutput` 对关闭）。
4. 后台或连接数限制使「空闲 3 + 在途 4 + SSE 2」无法维持一次 bootstrap 加一条 60 秒 SSE，而原因不是未实现的前后台策略（那是 I7，不是换传输栈的理由）。

没碰到这些，就不引入 SwiftNIO，也不要在一条 WSS 上做多路复用去「省连接」。省连接的办法是 50 秒空闲池，RFC 已把建连成本算在池上，不按请求计。

## G4.0 实测：回环鉴权不可行

2026-10-06 在 iOS 26 模拟器上用真实 `URLSession` 检查了系统代理和 Network 配置。目标是让 `https://127.0.0.1:<端口>` 在内层 TLS 首包之前完成本地鉴权。结果不成立。

- 直接连接回环 TLS 端口时，TCP 首包是 `16 03 01`。透明桥看不到 HTTP 路径或请求头，不能复用预览代理的 URL 密钥。
- `URLSession` 没有可注入的 socket factory、自定义 `NWParameters` 或协议栈插入点。`URLProtocol` 只能看到 URLSession 已交给它的请求，不能改写 TLS 前的字节。自定义 Network framer 只能加到直接创建的 Network 连接，加不到现有 `HostClient` 路径。
- 旧式 HTTP / SOCKS 字典、现代 SOCKS、现代 HTTP CONNECT、`matchDomains` 和 `NWParameters.PrivacyContext` 的代理配置都不能拦截 `127.0.0.1` 或 `127.0.0.2`。请求仍走 `lo0`，代理看不到首包。
- `kCFNetworkProxiesExceptionsList` 与 `kCFNetworkProxiesExcludeSimpleHostnames` 只在 macOS SDK 暴露，iOS SDK 没有关闭 `127.0.0.0/8` 绕过的配置。
- 非回环目标可以走 CONNECT：正确口令放行后的下一跳首包是 `16 03 01`；错误口令返回认证失败；缺口令或代理关闭时不放行，也不回退直连。但 `https://127.0.0.1` 即使配置了同一代理，仍直接连接目标 443，代理计数不变。因此不能把插件地址改成非回环地址来宣称回环鉴权通过。

`LocalGatewayAuthTests` 固化了后两条边界。它不连接中继、不读取配对数据，也不证明双层身份、压缩、背压、关闭或连接预算。这些项目都依赖先通过的回环鉴权，所以 G4.0 在第一项停止。

## 本阶段不做

- **不实现 I5.3**：远程首配、二维码 `remote`、bootstrap 对远程字段的增删、中继错误码只提示不删凭据。
- **不实现 I5.4**：主地址 → Tailscale → 中继、`NWPathMonitor` 作废缓存、Wi-Fi / 蜂窝切换。换网时驱逐池是 I5.4 的事；本文只定池的形状和额度。
- **不写**回环桥、`URLSessionWebSocketTask`、选路或配对代码。
- **不连** `relay.dshlinks.com`，也不做 PLAN 原文里的「经官方中继拉 bootstrap + SSE 60 秒」。那一步要等本结论确认，并且用隔离 `stateDir` 的 host，不能用维护者的日常中继会话。

## 原方案 A 的实现要点（G4.0 未通过，不进入实现）

1. 回环只听 `127.0.0.1` 随机端口；每条 accepted TCP 一条 WSS，禁止在任务上复用第二条流。
2. 池参数固定为 Android 同款：空闲 3、保留 50 秒、短请求在途 4、每主机 SSE 2，总额不超过每设备 12。
3. `DEVICE_LIMIT` / `SERVER_BUSY` / `RATE_LIMITED` 同路径退避；`UNKNOWN_KEY` / `BAD_MAC` 只提示（§7.4）。
4. 验收仍按 PLAN：隔离 host，一次 `GET /dsh-link/mobile/bootstrap`，一次 SSE 保持 60 秒。外加一条负例：故意停读时桥的缓冲有界。
